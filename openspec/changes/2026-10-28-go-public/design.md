# Design

## Context

The repository is private with two shipped releases (v1.0.0, v1.1.0) and a
proven tag-triggered release workflow. The audit (see proposal.md — Why)
found no secrets in history and no debug surface in the app, but no license,
no changelog, one-line release notes, the completed v1 `project-plan.md` at
the root, no contributing/CI/issue boilerplate, and no ideas parking lot.
Constraints: no new Dart dependencies; no app behavior changes except the
launcher icon; this environment has no `gh` CLI/token and the GitHub MCP is
read-only for releases, so anything that must happen on the GitHub side
(existing release notes, repo settings, the visibility flip) is a user
step with drafted inputs.

## Goals / Non-Goals

**Goals:**
- The repository is self-explanatory to a first-time visitor: license,
  changelog, contributing, security, ideas, archived plan — all linked from
  the README.
- Future releases carry real release notes generated from the changelog.
- The launcher icon is redesigned per the maintainer's pick and applied
  consistently at every density and in the adaptive icon.
- CI gates pushes and pull requests on the same analyze + test the release
  workflow already runs.

**Non-Goals:**
- Flipping the repository to public and the GitHub settings (description,
  topics, social preview, Discussions) — user steps in the GitHub UI.
- Cutting a new release; the icon change lands on master and ships with the
  next `v*` tag.
- App screenshots from a device/emulator are captured if a device is
  reachable; otherwise they become a follow-up user step.
- No changes to app runtime behavior, the Mistral layer, or storage.

## Decisions

**D1 — MIT license (user decision).** MIT over Apache-2.0/GPL-3.0: simplest
permissive license, F-Droid-compatible (the plan's distribution table lists
F-Droid), and it matches a personal project. Copyright holder: Wesley
Hendriks, 2026 (inferred from the commit email domain; correctable in a
follow-up commit if wrong).

**D2 — Keep a Changelog format with `v`-prefixed headings.** `## [v1.1.0] -
date` (not `## [1.1.0]`) so the release workflow can match the section by the
pushed tag name directly. An `## [Unreleased]` section accumulates changes
between releases.

**D3 — Release notes generated by the workflow, existing notes drafted by
hand.** The workflow extracts the `## [<tag>]` section from CHANGELOG.md with
awk and falls back to the current one-liner when the tag has no section.
The two existing releases predate this and have no changelog section, so
their notes are drafted under `docs/release-notes/` for the user to paste in
the GitHub UI (the MCP here cannot edit releases). Alternative considered:
re-creating the releases — rejected, it would orphan the existing asset
download URLs and history.

**D4 — project-plan.md moves to `docs/project-plan.md`, not deleted.** All
phases are checked off, but the plan holds the vision, architecture diagram,
tech-stack rationale, and the §9 ideas that seed `docs/ideas.md`. It stays
as the historical record with a header note; the archive's prose references
to it stay valid (they are not links). Only `README.md` and
`docs/friction-list.md` contain real links to fix.

**D5 — `docs/ideas.md` as the parking lot.** In-repo (versioned, visible,
linked from README) rather than GitHub Discussions-only: Discussions need
enabling and fragment the record; the file is the intake, OpenSpec proposals
are the execution. Community ideas can be mirrored in later. The file is
seeded with project-plan §9, the open dogfood observation (session lost when
the battery exemption is revoked mid-session), and the cancelled Phase-0
spike questions.

**D6 — CI mirrors the release workflow's first-party Flutter setup.** No
third-party Flutter action (the previous one disappeared and broke action
resolution — recorded in release.yml's header). CI needs only the Flutter
SDK (no JDK/Android SDK: analyze and VM tests don't build Android), pinned
to the same `FLUTTER_VERSION` and `ubuntu-24.04` as release.yml so the gate
matches the release gate.

**D7 — Icon options are generated, then the maintainer picks.** Three
vector-first designs rendered with ImageMagick at 512² for review; after
the pick, the same geometry is rasterized to the five mipmap densities and
expressed as the adaptive-icon foreground vector (108dp canvas, glyph inside
the 66dp safe zone), keeping the raster and vector forms consistent. The
orange `#FF7000` background stays — it is the brand anchor; the redesign
changes the glyph.

**D8 — Repo presentation assets derive from the final icon.** README header
and the 1280×640 social preview are generated from the chosen icon after
the pick (tasks 6.1–6.2). Screenshots need a device; if none is reachable
they become a follow-up user step rather than blocking go-public.

## Risks / Trade-offs

- [Risk] The awk changelog extraction mis-parses a section (heading format
  drift) → Mitigation: the extraction matches the exact `## [<tag>]` prefix
  and falls back to the default note; the workflow fails loudly on `gh`
  errors, and the first tagged release after this change verifies the
  path end-to-end.
- [Risk] CI without JDK/Android SDK fails on some plugin test →
  Mitigation: the suite is designed to run without the live API and with
  injected seams for platform channels; if a test needs more, the workflow
  gains the setup step (same pattern as release.yml).
- [Risk] The icon pick stalls the change → Mitigation: tasks 5.3+ and 6.x
  are blocked on the pick only; everything else completes independently, and
  the v1.0 waveform icon remains valid until then.
- [Risk] Copyright holder name is wrong → Mitigation: single-line fix in
  LICENSE; flagged to the user in the summary.
- [Trade-off] Release notes for v1.0.0/v1.1.0 are pasted by hand → accepted;
  one-time cost, no tooling available in this environment.

## Migration Plan

No migration: all changes are additive files plus link fixes and one
workflow edit. Rollback is `git revert` of the change's commits. The repo is
flipped to public only after the user completes the checklist in tasks.md
group 7 (paste notes, settings, social preview) — nothing here depends on the
repo already being public.

## Open Questions

- Which icon option the maintainer picks (blocks tasks 5.3+ and 6.x only).
- Whether a physical device is reachable for screenshots (task 6.3);
  otherwise a follow-up.
- Whether to enable GitHub Discussions with an "Ideas" category at
  go-public time (user step; the parking lot works without it).
